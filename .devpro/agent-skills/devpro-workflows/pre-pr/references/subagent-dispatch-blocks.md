# Subagent Dispatch Blocks (devpro:pre-pr)

Cold detail: the two full `Agent({...})` dispatch prompt blocks used by `devpro:pre-pr`. Load this file when you reach Step 3 or Step 5.5.3 in the SKILL body — the body tells you when and with what preparation; this file gives the literal dispatch payload.

## Step 3: dp-reviewer dispatch (Six-Axis Review)

Call the `dp-reviewer` subagent to execute six-axis + security review:

Exact authority fields copied into the prompt:

- **Manifest refs after classification**: When `classify-bounded` returns `route=full`, `repair_delta_manifest_ref` and `dependency_closure_manifest_ref` MUST be exact `null`, including when manifests were already sealed and any `full_reopen_reason` selected full review. Clear both prompt refs before dispatch; the reviewer MUST echo both as `null` in `receipt_payload.scope`. A `route=bounded` dispatch MUST carry both non-null sealed refs. 封存並傳入 classifier 的 refs 是分類輸入，不是 full reviewer payload 的 scope；以最終 route 準備派工欄位。

- **Bounded material preparation**：依 `code-review-checklist.md` §小修與 bounded 複審範圍，以 predecessor HEAD 起的 sealed repair delta 準備窄包；full `touch_list`／`done_when` 僅供需求 referent，不擴大閱讀範圍。

- `dispatch_id`／`round_number`／`risk_shape_digest_sha256`／`risk_shape_digest_alg`: exact `classify-bounded` result；reviewer MUST NOT guess, invent, or rewrite
- `dispatch_id` MUST be the 64-hex SHA256 logical dispatch digest from `classify-bounded` (`canonicalJsonV1`); MUST NOT be a UUID or hand-authored id. It is HEAD-sensitive (the digest input includes `head_sha`) — MUST NOT commit between obtaining it and calling `dp-reviewer`; if a commit is unavoidable, re-run `classify-bounded` afterward for a fresh `dispatch_id` (see SKILL.md Step 3 `` `dispatch_id` HEAD 敏感性``) — this exit does not apply to a `route=bounded` dispatch with sealed manifests (`classify-bounded` and receipt sealing both verify the manifest with `current`, so a post-seal commit leaves it stale and not re-sealable); record the classification in gitignored notes instead of a commit, and a `route=full` dispatch without manifests keeps this exit unchanged.
- `route=bounded` dispatch MUST carry non-null `repair_delta_manifest_ref` and `dependency_closure_manifest_ref` (sealed manifest paths+digests)；null refs 是合法值（首輪 `previousReceiptRef: null` 與 mandatory full receipt 以 exact null 攜帶），但 rereview 時 null refs 不是 route 探測：先封 manifests 再跑 `classify-bounded`（見 Prep 第 2 步）。Manifest 產法 MUST 依 `code-review-checklist.md` §Bounded Rereview Manifest Production（欄位意義＋三層 digest＋`seal-manifest`／`verify-manifest` request 形狀）；`node .devpro/scripts/review-remediation-evidence.mjs --help` 為輔助入口；`review-remediation-evidence.test.mjs` fixture 是 regression 載體、不是產法指引
- `receipt_payload.scope` 欄位集（exact five keys）：`risk_shape_digest_sha256`／`risk_shape_digest_alg`／`open_finding_ids`／`repair_delta_manifest_ref`／`dependency_closure_manifest_ref`；`risk_shape_digest_alg` MUST echo `classify-bounded` 的 exact 值（MUST NOT guess／invent／改寫），缺欄在 capture 以 `raw-payload-invalid — scope.risk_shape_digest_alg is required` fail fast；`open_finding_ids` MUST 為無重複的非空字串並依 code-point 嚴格遞增排序（字串序而非數字序，空陣列合法），否則 capture 以 `raw-payload-invalid` fail fast
- **Declared path（session cwd 非 `.worktree/<change_id>`；全 host 一等公民）**：prompt 於六欄之外、canonical 位置 `return_and_stop` 與 `role` 之間另帶 `change_id: <id>`（A2）與 `execution_root: <absolute binding worktree path>`（全 role 必帶）；兩值 MUST 由唯讀 helper `node .devpro/scripts/resolve-admission-binding.mjs <change_id> --cwd <session-cwd> --json` 預解析、不得手抄（缺 `execution_root` → `execution-root-required`；realpath 不符 → `execution-root-mismatch`）。cwd fast path（真 `.worktree/<id>` session cwd）豁免且 `change_id` 可省略；`EnterWorktree`／另開 rooted session／`session_move` **不是** gate 條件，binding 由同 common-dir exact-one `.worktree/<change_id>` 決定，record 落該 worktree。**Change-less 變更**的 `change_id` 取值、兩條 binding 路（cwd fast path 或本段 declared path）與 `change-dir-absent` 放行語意只定義在 `model-delegation.md` 的「Change-less 變更的 `change_id`」段；本檔的六軸 dispatch 只在 full rigor 執行，在此遇到的 change-less 形狀只會是 chore-A（依下方 Prep 第 3 點記 `receipt_authority_unavailable: chore_a_no_openspec`）。
- Append an exact completion contract to the prompt: return one duplicate-free UTF-8 JSON object only, with the v3 13 required base keys `change_id,responsibility_id,dispatch_id,reviewer_identity,review_authority,output_evidence,review_mode,round_number,bounded_rereview_count,lineage,scope,findings,verdict` plus required `guarantee_assessment` metadata; reviewer MUST set the producer-only `review_authority` and `output_evidence` placeholders to `null`, with no prose or code fence; `reviewer_identity` MUST be exact `{role:"dp-reviewer",executor_kind:"runtime-agent"}` (or the declared executor_kind for this lane) — missing `executor_kind` is an unqualified round (failed／re-dispatch), not a TL hand-normalization opportunity; every new `executor_kind: "runtime-agent"` raw payload MUST also carry the conditional top-level `execution_root_head` (40-hex, equal to the admission record `head_sha` — the reviewer attests the resolved binding root HEAD; a missing or differing value fails closed with `receipt-authority-changed`, while historical payloads that predate the key stay readable); each `findings[]` entry MUST carry exactly four keys — `finding_id`, `state`（open|closed）, `disposition`（state=open → `null`）, `observation`（`axis`／`severity`／`carrier`／`anchor`／`detail`／`evidence`，另可選填 `requirement_scope`：`in-scope`／`out-of-requirement`／`scope-unresolved`，缺鍵＝in-scope）; `observation_hash_sha256` is seal-derived and MUST NOT appear in a finding or its observation
- Append the guarantee assessment contract to the actual prompt: new v3 raw payload additionally requires top-level `guarantee_assessment` (outside findings/observations), exact object keys `schema,reviewed_target,dispatch_id,assessments`; schema=`devpro.review-guarantee-assessment/v1`, target=reviewed HEAD, dispatch=exact handoff ID. Each assessment has exact `finding_id,guarantee_ceiling,classification,rationale`; strings nonblank/trimmed, IDs unique and equal all payload finding IDs, empty findings → empty assessments. Name the existing owner and promised mechanical/cooperative checks and limits; classification exactly `within-ceiling|above-ceiling|unresolved`. Unknown → unresolved, never default PASS; above requires a reasoned TL ruling, never auto severity downgrade/closure or waiver of security/compliance, overclaim or spec/code contradictions. Keep requirement_scope and immutable observations unchanged. Normative schema/action SSOT=`openspec/specs/code-review-checklist/spec.md` Requirement: Review Guarantee Assessment Transport And Consumption; `review-guarantee-ceiling.md` and this copyable block are transport projections; historical payload without this key remains readable but new acceptance requires it. TL MUST run `review-guarantee-assessment.mjs --receipt <actual-receipt>` before accepting the new report.
- Append the evidence-document severity instruction to the prompt: for any finding whose carrier is this change's own evidence documents (proposal／design／decisions／tasks／qa-test-scope／notes evidence), the reviewer MUST state in that finding whether the error would change any reader's conclusion about this change; if it would not, severity is `Suggestion`, otherwise severity follows the actual consequence. This sets no cap on how many findings may be raised and never suppresses one — it only makes severity track consequence instead of how easy the error was to find.

The six leading `key: value` lines remain the legacy named-agent header, but a Codex `agent_type=dp-reviewer` MUST additionally use the SKILL body's prepared-intent flow; the header is not a substitute. On the declared path the two conditional lines (`change_id`／`execution_root`, canonical position between `return_and_stop` and `role`) join the header and the same gate enforces them (`execution-root-required`／`execution-root-mismatch`); a cwd-fast-path dispatch omits both — the six required fields stay unchanged and the conditional pair is never always-required. The pre-tool gate consumes the exact prepared intent and writes admission v2 under `<change_dir>/admission-records/`. Keep the returned `admission_record: <record_id> sha256=<digest>`; if the model-visible spawn response omits that handoff after intent consumption, keep the reviewer running and use `node .devpro/scripts/issue-codex-reviewer-admission.mjs --recover <request-file>` with exact schema `devpro.codex-reviewer-admission-recovery-request/v1` and ordered keys `schema,change_id,intent_id,intent_sha256` to follow the consumed claim to the same verified record. MUST NOT interrupt the reviewer, issue a replacement intent, scan records, or mint authority. That `record_id` becomes the `seal-receipt` request field `admissionRecordId` (runtime-agent receipts only; `executor_evidence` is producer-derived and MUST NOT be hand-filled). When the change requires independent judgment, run `verify-receipt` with `requireIndependence: true`; `tl-direct` / `legacy-unattributed` fail closed there.

**Ordinary／advisory（seams `no-ticket-ordinary-all-hosts-v3` + `host-dp-reviewer-primary-second-review-only-v1`；見 SKILL Independence pre-gate）**：任何 host 無券＝ordinary／advisory，六軸 findings 可用；缺票 MUST NOT 擋 spawn／wait，MUST NOT 丟棄 findings／六軸。**Primary**＝該 host-native `dp-reviewer`（Cursor Task pass-through＝ordinary 範例；Claude／Codex host native mint→seal 仍是 primary）。Claude／Codex **CLI** **只**經 Step 5.5 `dp-second-reviewer` sticky，**MUST NOT** 替代 primary。ordinary／無券 primary＋`risk_classes ≠ none` → sticky **必跑**且 **MUST NOT** 豁免；僅 sealed `requireIndependence: true` primary 才得豁免 sticky。`run-codex-primary-review-operator`／`codex exec` **MUST NOT** 當跨 host primary 入口。

Prep before this call (see SKILL body Step 3 for the full sequencing):

1. Read the active proposal (change name derived from `git branch --show-current` minus prefix): `proposal.md` (or `proposal-mini.md` for B-mini) under `openspec/changes/<name>/`; if the active folder no longer exists but is archived, read the latest `openspec/changes/archive/<date>-<name>/proposal.md` (rerun/recovery only). Extract `touch_list` (Touch 清單) and `done_when` (Target State). If no proposal/proposal-mini exists and this isn't chore A, block and return to the OpenSpec artifact step.
2. 首輪（尚無 predecessor sealed receipt，`previousReceiptRef: null`，`initial_review`）兩份 manifest refs MUST 為 `null`（initial dispatch 契約拒收非 null），不封 manifests。之後每輪 rereview：先封 manifests 再跑 `classify-bounded`（both `repairDeltaManifestRef`／`dependencyClosureManifestRef`，即 repair-delta／dependency-closure durable refs；manifest `validator` 宣告自 change base 未變動、實際計算 manifest digest 的工具並以 `pre-existing-trusted` 封存，例如 `.devpro/scripts/lib/primitives.mjs`（`sha256Hex`）；宣告已變動的 review trust surface 須帶 `independently-verified-same-change` evidence，目前沒有 CLI 產生入口）；null refs 不是 route 探測：只有 seal 無法完成時（例：lineage 改變使 `surface_base_sha` 不符前一輪 head，或 validator trust surface 變動而 production oracle 無法獨立驗證）才傳 `null`；此時依 classifier 結果走——可派工 `route=full`（如 `git_lineage_changed`／`validator_trust_surface_changed`）照派；不可派工的 `full_reopen_required`／`manifest_refs_absent` 表示 manifests 其實可封，先封再 rerun，不是已取得 full dispatch。取得後 dispatch exactly `full|bounded|handback`; bounded predecessor matches equal prior complete open IDs。後繼輪（`previousReceiptRef` 非 null，含 full）prompt MUST 填 `previous_receipt_ref` 與 predecessor `open_finding_ids`；`findings[]` MUST 含 predecessor 的必帶集合（SSOT checklist）與本輪新 finding，更早已 closed 的其他 finding MAY 省略、MAY 重帶（reopen＝`state: open`＋`disposition: null`），full 輪 MUST 沿用 predecessor 的 `finding_id`、MUST NOT 以新 ID 取代，漏帶回 `predecessor-finding-omitted`。Step 3 primary full MUST review committed active artifacts before archive。same-agent continuity is an optimization and MUST NOT be correctness authority；transcript/manual claims亦非authority。Valid Git/durable archive transition never dispatches a second reviewer；only invalid/non-equivalent/transition後commit routes `full_reopen_required`。Step 5.5.3 unchanged。
3. **Receipt-authority dispositions（SKILL Step 3）**：若尚無 sealed receipt → `receipt_authority_restart: missing_predecessor_seal`（`previousReceiptRef: null` bootstrap；seal 後 `classify-final`／`seal-final` 只看新 sealed lineage）；若 chore A 無 OpenSpec folder → `receipt_authority_unavailable: chore_a_no_openspec`（`route=risk_shape_unavailable`；mutable envelope + PR Review Summary；不 seal）。**MUST NOT** invent `dispatch_id`。

On reviewer response後 (blocked / partial / finished)：第一個動作 MUST 落盤收到的 exact JSON 原文 bytes 至 `<main-checkout-root>/notes/review-<change>-r<N>.md`（mutable raw source；不得改寫、摘要或插入 `transport_invocation_id`、prose、code fence）。runtime 若回傳 exact ID，MAY 另記 optional `transport_invocation_id`，但 MUST NOT 作 auth／provenance／authority。接著 MUST 以 exact camelCase request 執行 `node .devpro/scripts/review-remediation-evidence.mjs capture-reviewer-output` 取得 immutable raw ref，再由 producer 只填 `review_authority`／`output_evidence` 並執行 `node .devpro/scripts/review-remediation-evidence.mjs seal-receipt`；其餘欄位必須與 raw canonical-equal。Mutable `.md` alone 無法通過 `walkReceiptAuthorityChain`。**例外**：已記錄 `receipt_authority_unavailable: chore_a_no_openspec` 時 MUST NOT 跑 seal-receipt。不得由摘要重建 reviewer payload：

- **blocked** (has Critical) → fix；先封 manifests 再跑 `classify-bounded`（seal both manifests before rerunning; null refs 不是 route 探測，見 Prep 第 2 步）取得 route。當 current Git/risk authority 與 predecessor receipt 可分類時，已記錄的 `postDispatchDiscovery=new_critical|out_of_manifest_carrier|wording_repair_substantive` 會由 classifier 回傳 `route=full` 與 exact `dispatch_id`，再走完整六軸；`record_observation_required` 必須先落盤 observation。`full_reopen_debug_reason` **MUST NOT** be read as a routing signal; it is for human diagnosis only. `full_reopen_required` 與 `risk_shape_unavailable` 都沒有 dispatch authority，依各自診斷修復／停下，不得派 reviewer；`bounded`→只 dispatch bounded scope、`handback_required`→handback。見 `node .devpro/scripts/review-remediation-evidence.mjs --help`。
- **partial** (`important_findings[]` non-empty) → report to the user；若核准修復，先封 manifests 再跑 `classify-bounded`（null refs 不是 route 探測，見 Prep 第 2 步）取得 route 分類。
- **finished** → terminal no-blocking receipt成立後proceed to Step 3.6；不得先archive。payload 仍有 open finding（含 Suggestion）時，Step 3.6 的收斂檢查會擋下 archive，先關閉再進。

**再審 reviewer 的選擇**：同責任的 bounded 再審 `continue` 上一輪的 reviewer thread（`SendMessage`／`followup_task` 帶 `instance_mode: continue` 與 `parent_record_id`；`to` 取自原 spawn 回傳的 agent id、`parent_record_id` 取自同一 thread 上一輪已 admitted 的 record（首次續作為該 spawn 回傳的 record，其後為上一次續作訊息回傳的 record，不是每輪都回到 fresh 根）），經 receipt 端 chain 驗證可封存。未宣告的續作沒有 admission record，無法封存。build 回 `receipt-authority-invalid` 先核對 `admissionRecordId` 是該輪 dispatch 回傳的 record（build 不寫入，可重跑）；record 本身的 chain 有誤（例如續作宣告填錯 `parent_record_id`）則走上方「收到 reviewer 回報後」的既有失敗路由：該輪已發布 raw 作廢且不可刪，full 輪 commit 後重跑 `classify-bounded` 取新 `dispatch_id` 再派，帶 sealed manifest 的 bounded 輪不可重封、交回 operator；reviewer 回覆之後才寫出的續作 record 不得綁本輪 raw。

gitignored 修復載體不在 diff 內：dispatch 給檔案路徑、要求讀檔驗證，MUST NOT 給結論句。

Fallback routing：首次 first review=full、完整六軸；classified full→完整六軸；bounded→open IDs + fresh repair-delta + immutable dependency-closure only；handback→交回。使用者授權後 exact override 在沒有 independent reopen 時取得一次 `route=bounded`（`handback_authorized_bounded`）；只有 independent reopen 成立時才取得 `route=full`（`handback_authorized_full`）。走完 handback→bounded→final：封合格 `finished` 後 `classify-final` 可達 `final_ready`；post-cap bounded receipt 缺同 responsibility＋dispatch 的 consumed override claim 時 seal／chain walk 必須失敗。Main agent 執行同一 route 並保留 Critical gate。

**覆蓋輪（coverage-only round）的便宜路**：某一輪只是為了讓收據涵蓋新的 reviewed head 才存在，其 delta 限於 `evaluateRegressionHeadCurrency` 的 R6 bookkeeping 允許集（例如 `tasks.md` 的勾選或證據行；經核對為零行為變更）、change 的 `risk_classes` 為 `none`、不要求獨立判斷、且依 `model-delegation-delegation-rules.md` 決策序判為 TL-direct（不屬 `fresh` 觸發條件）時，先封 manifests 並由 `classify-bounded` 簽發 `route=bounded`，再只核對新 HEAD 的 bookkeeping delta 與必要 dependency closure；MUST NOT 為取得覆蓋而重掃整包或新派 reviewer。仍完整驗證兩份 manifest、前輪鏈、exact-HEAD、Critical/Important 與既有輪數上限，以 `seal-receipt` 封 `reviewer_identity` 的 `executor_kind: tl-direct` 收據（`executor_kind: tl-direct` MUST NOT 傳 `admissionRecordId` 或 `attestationRef`，與 runtime-agent 相反）。`tl-direct` 收據不滿足 `requireIndependence: true`，所以任何要求獨立判斷的 change 仍須走 `dp-reviewer`；mandatory-full 或資格不符照既有路由。比例規則 SSOT：`openspec/specs/code-review-checklist/spec.md` 的 `Coverage-Only Rereview Work Is Proportional Without Relaxing Authority`。

### `receipt_payload.findings[]` 格式對照範例（避免常見 4 種偏移）

`seal-receipt` 對每個 finding 跑 `assertExactKeys`（`review-remediation-evidence-core.mjs`），下列 4 種偏移最常見（同一 reviewer role 首次派工常一次過，第 3 輪起才踩，見 issue #2418）。合規範例（`state: "open"` 形狀）：

```json
{
  "finding_id": "F-a1-example",
  "state": "open",
  "disposition": null,
  "observation": {
    "axis": "1",
    "severity": "Important",
    "carrier": "path/to/file.mjs",
    "anchor": "L42",
    "detail": "bounded text describing the observation",
    "evidence": ["path/to/file.mjs:40-45"],
    "requirement_scope": "in-scope"
  }
}
```

**`observation.evidence[]` 形狀（MUST）**：每項 MUST 為 bare repo-relative path（open finding MAY 帶 `:line`／`:line-range`；closed-Critical 須為 bound HEAD 可解析的裸 path），說明文字 MUST 置 `observation.detail`；判定以 core `assertSafeRepoRelativePath` 為準，本段只文件化、不改變 validator 行為。

**Critical 的 `observation.anchor`（MUST）**：須是 `carrier` 內容的 literal 子字串，且修復後仍存在於 bound HEAD（例如穩定的 heading／識別字）；不得引用有缺陷的那一句原文——修後該句消失，closing receipt 的 anchor 驗證即報 `Critical closure anchor is stale or absent`；本段只文件化、不改變 validator 行為。

**此範例只適用 open（或 closed 但非 Critical）finding。** `state: "closed"` + `severity: "Critical"` 另有 bound-HEAD 綁定要求（`carrier`／每個 `evidence` 皆須在 `lineage.head_sha` 可解析、`anchor` 須為 `carrier` 內容的 literal 子字串，且 in-scope／未標 `requirement_scope` 的 `disposition` 只能是 `fix-now`／`non-issue-with-evidence`；`out-of-requirement` 另可為 `tracked-follow-up`，`defer-with-owner-trigger` 對任何 scope 都不得關閉 Critical）——見 `code-review-checklist.md` §Bounded Six-Axis Rereview Cadence 與 R11，不要把上面的 `anchor`／`evidence` 形狀直接套用到 closed-Critical finding。

四種常見錯誤（逐一比對合規範例的對應欄位；除第 4 條外，實際錯誤訊息皆帶 `reviewer_payload.findings[<index>].` 前綴）：

1. **open finding 卻帶非 null `disposition`** —— `state: "open"` 時 `disposition` MUST 為 `null`（不是 `"tracked-follow-up"` 之類的值，那要等 `state` 轉 `"closed"` 才填）。錯誤示範：`{"finding_id": "F-x", "state": "open", "disposition": "tracked-follow-up", "observation": {...}}` → capture／seal-receipt 報 `open finding disposition must be null`（產端前移；不得只靠踩 seal-receipt）。
2. **`observation` 夾帶 schema 外欄位** —— `observation` 的 exact key set 是 `["axis", "severity", "carrier", "anchor", "detail", "evidence"]` 加選填 `requirement_scope`（缺鍵＝in-scope；v3 收據才接受，值只能是封閉三值之一）；**不得**額外塞 `carrier_class`／`observation_hash_sha256` 之類欄位。`observation_hash_sha256` 是 `seal-receipt` 在 seal 當下另外計算、寫入頂層 `observation_hashes[]` 的欄位，**不該**由 reviewer 塞進 `observation` 裡；`carrier_class` 則是完全不同用途的欄位（cross-model sticky packet）。錯誤示範：`"observation": {"axis": "1", "severity": "Important", "carrier": "...", "anchor": "...", "detail": "...", "evidence": [...], "carrier_class": "code", "observation_hash_sha256": "64-hex"}` → seal-receipt 報 `observation has unknown or missing fields`。
3. **closed finding 把 `severity` 寫成 `"OK"`** —— `severity` 的 exact enum 是 `Critical | Important | Suggestion`，即使 finding 已經 `state: "closed"` 也要保留原始（修復前）severity，**不得**改寫成 `"OK"` 表示「已解決」；「已解決」這個語意由 `state: "closed"` + `disposition` 承載，不是改寫 `severity`。錯誤示範：`{"finding_id": "F-y", "state": "closed", "disposition": "fix-now", "observation": {"severity": "OK", ...}}` → seal-receipt 報 `observation.severity is invalid`。
4. **`scope.open_finding_ids` 未依本輪 state 更新** —— 這個陣列 MUST **精確等於**本輪 `findings[]` 中所有 `state: "open"` 的 `finding_id` 集合（不多不少），常見錯誤是沿用上一輪的舊清單、或漏掉本輪新開的 finding。錯誤示範：某 finding 本輪已改成 `state: "closed"`，但 `scope.open_finding_ids` 仍列著它的 `finding_id` → seal-receipt 報 `scope open_finding_ids must exactly match open findings`。集合對了仍可能失敗：陣列 MUST 無重複並依 code-point 嚴格遞增排序（字串序而非數字序，`F-x-10` 排在 `F-x-2` 之前），否則 `capture-reviewer-output` 在發布 raw payload 前就回 `raw-payload-invalid`（內部診斷碼 `open-finding-ids-noncanonical`，`prepare-post-hoc-attestation` 直接回報該碼）。

**closed-Critical 合法形狀**（不要把上面合規範例的 `"anchor": "L42"`／`"evidence": ["path/to/file.mjs:40-45"]` 套用到這裡——兩者在 open finding 合法，但 closed-Critical 分支會被 core 拒絕，因為 `anchor` 須為 `carrier` 在 `lineage.head_sha` 內容的 literal 子字串、每個 `evidence` 須能在該 HEAD 用 `git cat-file`／`git show` 解析，且 in-scope／未標 `requirement_scope` 的 `disposition` 只能是 `fix-now`／`non-issue-with-evidence` 兩者之一，範圍外見下段）。合法示範（取自本 change 自己 round 2 已 seal 的 receipt；`evidence` 實際共 5 條，下列為節錄前 2 條）：`carrier: ".devpro/scripts/test-suite-manifest.mjs"`、`anchor: "MANIFEST"`（該 carrier 內容的 literal 子字串）、`evidence: [".devpro/scripts/test-suite-manifest.mjs", ".devpro/scripts/lint-test-suite-manifest.mjs", "...（節錄）"]`（裸 repo-relative path，非 `path:line-range`）、`disposition: "fix-now"`。

**範圍外 closed-Critical 的另一合法形狀**：`requirement_scope: "out-of-requirement"` 的 Critical 可 `state: "closed"`＋`disposition: "tracked-follow-up"`，其 `carrier`／`anchor`／`evidence` 的 bound-HEAD 綁定與上列相同，`severity` 仍寫 `Critical`、不改寫；`scope-unresolved` 的 Critical 保持 `state: "open"`；bound HEAD 的 `decisions.md` `## Scope Rulings` 有 TL 裁示後，由下一輪 reviewer 記 `state: "closed"`＋`disposition: "tracked-follow-up"`，其 observation 全部欄位須與上一輪收據逐字相同（hash 綁整個 observation）；`defer-with-owner-trigger` 對任何 scope 的 Critical 都會使收據被擋。
